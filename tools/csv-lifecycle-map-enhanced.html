Computer System Validation - Risk-Based Assurance, Not Uniform Documentation Volume

Computer system validation establishes documented evidence that a computerized system used in a GMP process reliably does what it is intended to do, consistently and with appropriate control over electronic records and signatures. GAMP 5's second edition and FDA's 2022 Computer Software Assurance guidance both pushed the field toward critical thinking and risk-based effort allocation, moving away from the earlier assumption that more test scripts and paper automatically meant better assurance. A high-risk system genuinely affecting product quality or patient safety warrants rigorous testing; a low-risk administrative system does not need the same treatment.

Category 1 - Infrastructure Software

Operating systems, database engines, and other infrastructure software, typically qualified rather than fully validated as a standalone application.

Effort: Infrastructure qualification

Category 3 - Non-Configured Products

Commercial off-the-shelf software used as supplied, without configuration to the business process, verified largely through supplier assessment.

Effort: Supplier assessment, basic testing

Category 4 - Configured Products

Commercial software configured to meet specific business process needs, requiring testing focused on the configuration rather than the base code.

Effort: Configuration-focused testing

Category 5 - Custom Applications

Bespoke software developed specifically for the site, warranting the most rigorous lifecycle testing given the absence of prior commercial verification.

Effort: Full lifecycle testing

Risk-Based Effort Scaling

High GMP Impact, High Complexity

Custom or highly configured systems directly controlling product quality warrant the most rigorous scripted testing and full documentation.

GAMP 5 (2nd Ed.)

Moderate GMP Impact

Configured systems with indirect quality impact warrant testing focused specifically on the configured, business-critical functions.

FDA CSA Guidance 2022

Low GMP Impact

Administrative or non-critical systems warrant lighter-touch verification, often unscripted testing with simple documented evidence.

Validation Test Failure Response Steps

Step 1 - Document the specific failure Record precisely which test step failed, the expected versus actual result, and the system state at the time.
Step 2 - Determine root cause Investigate whether the failure stems from a configuration error, a genuine software defect, or an incorrect test script.
Step 3 - Assess impact on other completed testing Evaluate whether the failure calls into question the validity of other tests already executed and passed.
Step 4 - Remediate and re-test Implement the correction and re-execute the failed test, along with any other test affected by the same root cause.
Step 5 - Document resolution in the traceability record Update the traceability matrix and validation documentation to reflect the failure, root cause, and successful re-test outcome.

Data Integrity and CSA Principles

Audit trail review is routine, not exceptional Audit trail data reviewed as part of routine batch or record release, not only investigated when a problem is already suspected.
Critical thinking drives test depth Testing rigor determined by genuine assessment of patient and product risk, rather than defaulting to maximal documentation for every system.
Unscripted testing is acceptable evidence Ad hoc, exploratory testing accepted as valid evidence for lower-risk functions, provided it is appropriately documented.
Leverage supplier testing where justified Vendor testing and quality documentation leveraged with a documented rationale, avoiding duplicative re-verification of unchanged commercial code.

CSV Lifecycle Elements

System Inventory and Classification Complete inventory of GMP-relevant computerized systems, each classified by GAMP category and criticality.
Validation Plan and Summary Report Validation plan defining scope and approach at project outset, closed by a summary report referencing the complete evidence package.
Traceability Matrix Document tracing every requirement through specification and into the specific test that verifies it.
Electronic Signature and Audit Trail Configuration Part 11 compliant electronic signature and audit trail settings configured, tested, and documented.
Change Control Integration Validated system changes routed through formal change control, with revalidation scope determined by risk assessment of the change.
Periodic Review Schedule Defined interval for reviewing the system's continued validated state, incorporating incident history and any accumulated configuration drift.
Backup and Disaster Recovery Verification Backup and recovery procedures tested and documented, confirming GMP data can be reliably restored if needed.
Retirement and Data Migration Planning Defined plan for system retirement, including data archival or migration, preserving record accessibility beyond decommissioning.

Regulatory Text - Source Provisions

21 CFR 11.10(e)

Persons using closed systems to create, modify, maintain, or transmit electronic records shall employ procedures and controls including use of secure, computer-generated, time-stamped audit trails to independently record the date and time of operator entries and actions that create, modify, or delete electronic records.

EU GMP Annex 11, Section 4.2 (paraphrased - refer to the official Annex 11 text for exact wording)

Validation documentation should include change control records and results of any periodic evaluation, demonstrating the system remains in a validated state throughout its use, with a risk assessment approach used to determine the scope of validation.

FDA Computer Software Assurance Guidance, 2022 (paraphrased - refer to the official guidance for exact wording)

A risk-based approach that applies critical thinking to determine the appropriate level of assurance activities, including the use of unscripted testing methods where justified by the risk to patient safety, product quality, and data integrity.

Common Inspection Findings - Computer System Validation

Illustrative of recurring themes seen across published FDA 483s and warning letters. Not tied to a single specific citation.
Audit trail not reviewed as part of routine release Electronic batch or record release performed without evidence that the associated audit trail was reviewed as part of the routine release decision.
GAMP category not documented with rationale System validation records lacking a clear, documented rationale for the GAMP category assigned, making the resulting test scope difficult to justify.
Configuration changes made outside change control System configuration settings found to differ from the documented, validated configuration, with no corresponding change control record explaining the difference.
Periodic review not performed or overdue No evidence of periodic review confirming the system's continued validated state, despite significant time elapsed since initial validation.

Best Practice Guidance

Build audit trail review into the standard release checklist Add audit trail review as an explicit, named step in the routine batch or record release checklist rather than treating it as a separate, optional activity.
Document GAMP categorization rationale in the validation plan Require a written justification for the assigned GAMP category as a mandatory section of every system's validation plan.
Use configuration comparison tools where available Where the system supports it, use automated configuration comparison or baseline tools to detect drift from the validated configuration.
Maintain a master periodic review calendar across all validated systems Track every validated system's periodic review due date in a single, actively monitored calendar rather than relying on individual system owners to self-track.

CSV vs Computer Software Assurance

Traditional CSV historically emphasized comprehensive scripted testing and heavy documentation volume for every system. FDA's Computer Software Assurance approach retains the same underlying assurance goal but directs effort using critical thinking and genuine risk assessment, accepting unscripted testing where the risk profile supports it.

Validation vs qualification for computer systems

Qualification, in the equipment sense, establishes hardware functions correctly. Computer system validation is the broader activity confirming the complete system, software, configuration, and data controls together, reliably supports its intended GMP use.
